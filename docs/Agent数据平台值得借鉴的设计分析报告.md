# Agent数据平台值得借鉴的设计分析报告

## 一、报告目的

本报告基于现有数据平台与Agent数据平台的对比分析，聚焦Agent数据平台中对当前平台具有借鉴价值的设计。分析重点是这些设计能够解决什么问题，以及为什么值得在数据平台重构时予以关注。

Agent数据平台较有价值的设计主要集中在数据组织、版本管理和数据治理三个方面，包括Raw与Dataset分层、稳定样本ID、不可变版本、加工血缘、任务版本固定以及Schema与质量校验。

## 二、值得借鉴的设计

### 1. Raw与Dataset分层管理

Agent数据平台将未经处理的原始数据定义为Raw，将经过解析、清洗、标注、质检或特征提取的数据定义为Dataset。

Raw用于保留数据最初进入平台时的状态。例如，外部采集的图片、视频、音频、文档和压缩包首先作为原始版本保存。经过格式转换、质量过滤或人工标注后，处理结果以新的Dataset形式存在，而不直接修改原始数据。

这种设计能够明确区分原始数据与加工结果。同一批Raw数据可以形成去重版、质量过滤版、自动标注版、人工审核版或评测版等不同Dataset。每个加工结果都有明确来源，出现问题时仍然可以回到原始数据重新处理。

当前平台同时管理原始文件、文件元数据和多种加工结果。借鉴这一设计，有助于避免原始数据与派生数据边界不清、处理结果覆盖、重复加工以及数据来源难以确认等问题。

### 2. 稳定样本ID与显式多模态关系

Agent数据平台使用稳定ID标识数据样本，并通过显式链接描述文本、图片、视频、音频和标注之间的关系。

例如，一个图像编辑样本可能同时包含原图、参考图、生成图、Prompt、质量评分和人工标签。这些内容通过样本ID和明确的关系字段组织为一个完整样本。视频与关键帧、音频与ASR文本、PDF与提取文本之间也采用类似方式关联，而不是依赖文件名或目录结构推断。

文件路径适合定位存储对象，但路径可能因文件移动、重命名、存储迁移或Bucket调整而变化，不适合作为数据的长期身份。稳定样本ID能够保证数据在PostgreSQL、ClickHouse、OBS、Milvus以及不同数据集版本之间保持一致关联。

显式多模态关系还能够提高数据校验能力。平台可以检查某张生成图是否存在对应原图、某个视频关键帧是否属于有效视频，以及某段标注是否能够关联到正确的数据对象。

### 3. 不可变数据集版本与Manifest

Agent数据平台为每个Dataset版本分配独立的版本标识，并通过Manifest描述该版本包含的数据、Schema、来源和加工信息。

版本发布后，其内容保持不变。后续增加样本、删除低质量数据、修改标签或生成Embedding时，不直接修改已经发布的版本，而是形成新的Dataset版本。不同版本之间保留清晰的演进关系。

Manifest用于描述一个版本的完整状态，典型内容包括：

- Dataset和版本标识；
- 样本或文件清单；
- Schema及字段定义；
- 上游数据版本；
- 加工任务和处理配置；
- 模型及模型版本；
- 创建时间和创建者；
- 数据量、文件大小和质量统计。

这一设计的重要价值是保证结果可复现。仅保存数据集名称或查询条件，无法保证未来得到相同结果，因为底层文件、元数据或质量分可能发生变化。不可变版本和Manifest能够准确说明某次数据交付、模型训练或模型评测使用了哪些数据。

### 4. 数据加工过程的完整血缘

Agent数据平台将数据加工结果与精确的输入版本、处理任务、Pipe版本、模型版本和参数绑定，形成从原始数据到最终Dataset的完整血缘。

例如，一批图片经过质量检测和过滤后形成新的Dataset版本，该版本可以继续追溯到：

- 输入的Raw或Dataset版本；
- 使用的质量检测任务；
- 质量检测模型及模型版本；
- Prompt、阈值和其他处理参数；
- 任务执行时间和执行结果；
- 形成的输出Dataset版本。

数据质量问题不一定来自原始文件，也可能来自解析规则、标注过程、模型能力或参数设置。完整血缘能够帮助平台定位问题产生在哪个环节，并判断哪些下游数据集可能受到影响。

完整血缘还支持不同处理方法之间的对比。例如，同一批图片分别使用两个模型生成质量分时，可以保留两个独立结果版本，并比较模型差异，而不需要覆盖已有结果。

### 5. 任务输入输出版本固定

Agent数据平台在任务创建时固定输入数据版本，并在任务产生有效结果后记录输出数据版本。任务不会因为排队或执行期间上游数据发生变化而自动读取新的数据版本。

异步任务通常不会在提交后立即执行。如果任务只引用数据集名称、`latest`版本或动态查询条件，那么任务真正开始执行时，输入数据可能已经发生变化。此时，任务结果与用户提交任务时看到的数据并不一致，也难以解释结果差异。

固定输入版本可以保证任务始终处理提交时确定的数据。固定输出版本则可以明确任务产生了哪一份结果，并将其继续作为后续清洗、标注、质检、训练或评测任务的输入。

这一设计使每个任务都具有明确的数据边界，任务之间能够形成稳定的数据加工链，并提高异步处理结果的确定性和可审计性。

### 6. Schema契约与版本质量校验

Agent数据平台使用明确的Schema定义数据结构，并在Dataset版本形成过程中对字段、类型、样本ID、文件内容和跨模态关系进行校验。

当前平台使用JSON字段保存不同数据来源和模态的扩展属性，能够适应快速变化的业务需求。但随着数据类型和接入来源增加，可能出现同一字段使用不同名称、数值被保存为字符串、单位不一致、必填字段缺失以及Embedding维度不一致等问题。

Schema契约能够明确核心字段的名称、类型、含义、是否必填及约束条件，同时保留一定的扩展能力。这样可以使不同来源的数据在进入Dataset后具有一致的结构，降低后续查询、统计、标注和训练的数据处理成本。

版本质量校验则确保一个Dataset版本在发布时处于完整、可用状态，主要关注：

- 样本ID是否唯一；
- 必填字段是否完整；
- 字段类型和单位是否符合定义；
- 文件是否存在且能够正常读取；
- 文件内容哈希是否匹配；
- 标签与数据对象是否正确对应；
- 多模态链接是否有效；
- Embedding维度是否一致；
- Manifest记录与实际数据是否一致。

通过Schema契约和版本质量校验，平台能够在数据发布前发现结构和关联问题，避免不完整或不一致的数据继续进入交付、训练和评测环节。

## 三、总结

Agent数据平台值得借鉴的设计可以归纳为三个方面：

| 方面 | 值得借鉴的设计 | 主要价值 |
|---|---|---|
| 数据组织 | Raw与Dataset分层、稳定样本ID、显式多模态关系 | 明确原始数据与加工结果，保证跨系统和跨模态关系稳定 |
| 版本管理 | 不可变Dataset版本、Manifest、任务输入输出版本固定 | 保证数据交付、训练和评测使用的数据可以准确复现 |
| 数据治理 | 完整加工血缘、Schema契约、版本质量校验 | 说明数据来源和处理过程，提前发现结构、质量与关联问题 |

这些设计共同解决了数据平台中的几个核心问题：数据从哪里来、不同数据之间如何关联、经过了哪些处理、形成了哪个版本，以及该版本能否被准确复现和可靠使用。
